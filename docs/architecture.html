Architecture

Infrastructure components, data flows, and the trade-offs behind each choice. Use this to understand what you need, what's optional, and what to swap when you scale.

Infrastructure Components

PostgreSQL

Required

Serves two distinct roles:

  • Application data — recordings, users, AI sessions, shares (Doctrine ORM)
  • Message queue — the async Messenger transport uses Doctrine transport with LISTEN/NOTIFY for instant delivery without polling (transcription jobs)
Alternative: RabbitMQ can replace the message queue role. Symfony Messenger supports AMQP natively. Adds infrastructure cost but handles high message volumes better.

Mercure

Required

Server-Sent Events hub used for both browser streaming and internal IPC:

  • Transcription status — worker publishes progress updates, browser subscribes via EventSource
  • AI session output — pi.dev PTY output is published chunk-by-chunk to the browser terminal (xterm.js)
  • AI session daemon IPC — the web container publishes start/input/close commands to the ai-session-daemon topic; the daemon subscribes via SSE and routes them to the correct PTY

Routed same-origin at /.well-known/mercure to avoid CORS. The browser gets a JWT cookie via Authorization::setCookie to authorize subscriptions. The daemon uses a server-side subscriber JWT.

Alternative: WebSockets (more complex, bidirectional not needed for browser). Unix domain sockets or PostgreSQL NOTIFY for daemon IPC (but Mercure is already running and keeps the architecture DB-agnostic).

Vault KMS

Required (prod)

Encrypts and decrypts per-user AI provider API keys at rest. The api-keys endpoint provides transit encryption — the key material never leaves the vault.

Alternative (dev): APP_SECRET-derived encryption via sodium. Less secure since the key lives in the environment, but works without external services.

Network Storage

Required

Shared mount at /storage/audio for uploaded audio files. Both the web container (receives uploads) and the transcription worker (sends audio to Whisper) need access to the same files. Without shared storage, the worker can't read what the web container wrote.

OpenSearch

Optional

Full-text search alternative to PostgreSQL's built-in FTS. Controlled by the SEARCH_PROVIDER environment variable (postgres by default). Only worth adding when recording volume makes PostgreSQL FTS a bottleneck.

Redis

Not currently used

Could serve as a Messenger transport or session cache. Not needed at current scale since PostgreSQL handles the message queue and Mercure handles all real-time IPC.

RabbitMQ

Not currently used

Could replace the Doctrine transport for Symfony Messenger if message volume or delivery guarantees require it. Messenger supports AMQP out of the box.

Why both Mercure and PostgreSQL?

Mercure (SSE) is fire-and-forget: if no subscriber is listening when an event is published, it's gone. This is fine for AI session IPC (keystrokes, start/close commands) because the user sees immediately if something didn't work and can retry.

Transcription jobs need durability: if the worker is restarting during a deploy when a recording is uploaded, the job must not be lost. Symfony Messenger with the Doctrine transport stores messages in a database table and delivers them when the worker comes back. It also provides automatic retry with backoff and a failure transport for dead-letter inspection.

Rule of thumb: use Mercure for real-time IPC where loss is tolerable, Messenger for background jobs where reliability matters.

When to Swap What

Everything runs on PostgreSQL + Mercure today. Here's when each component should be replaced.

Bottleneck Current Swap to When
Message queue throughput Doctrine transport (PostgreSQL) RabbitMQ (AMQP) High message volume, need dead-letter queues, priority routing
Session IPC (start/input/close) Mercure publish/subscribe Redis Pub/Sub or Unix sockets Very high message rate per session, or need delivery guarantees (Mercure SSE is fire-and-forget)
Full-text search PostgreSQL FTS OpenSearch Large recording corpus, need fuzzy matching, faceted search, or relevance tuning
API key encryption Vault KMS (prod) / sodium (dev) External KMS (AWS, GCP) Multi-cloud deployment, compliance requires HSM-backed keys
Audio storage Upsun network-storage S3-compatible object store Need CDN, cross-region replication, or very large file counts
